# 要件定義: Tango MVP

> 状態: **レビュー待ち**
> 原典: [`../Tango_requirements.md`](../Tango_requirements.md)
> 本書は原典を実装・テストで追跡しやすい形に正規化した要件ベースラインである。原典の「要確認」を確定仕様へ読み替えない。仕様を変える場合は原典、本書、関連設計を同じ変更で更新する。

## 1. 背景・目的

Tango は、自分で登録した英単語と複数の日本語の意味を、文字入力テストで反復学習する個人向け Web 単語帳である。

中心価値は次の3点とする。

1. 1つの英単語に複数の日本語の意味を登録できる。
2. 回答履歴から苦手な単語と習熟度を把握できる。
3. 完全一致、決定的な正規化一致、AI意味判定をこの順で使い、不要なAI呼び出しを避ける。

成功は、Googleログインから単語登録、テスト、履歴保存、一覧での習熟確認までの主要動線が、ユーザー間のデータ漏えいなく完了することで判断する。

## 2. 対象ユーザー

- 英語ドキュメントやWebページで出会った未知語を、自分専用の単語帳へ蓄積したい人。
- 選択式ではなく、日本語の意味を自分で入力して定着させたい人。
- MVPは個人利用を想定するが、データはアカウント単位で厳密に分離する。

## 3. スコープ

### 3.1 MVPに含める

- Better Auth と Google OAuth によるログイン、ログイン必須制御。
- ユーザー単位で分離された単語・複数意味・任意ヒントのCRUD。
- 翻訳候補をフォームへ反映し、確認後に保存する登録補助。
- 完全ランダム／苦手優先の2モードによる文字入力テスト。
- 完全一致 → 正規化一致 → AI意味判定の段階的な正誤判定。
- 回答、正誤、判定種別、ヒント利用有無、回答日時の履歴保存。
- 単語別の正解率、正解数／回答数、未回答状態、習熟カード色。
- 将来のChrome拡張から再利用できる認証済みREST API境界。

### 3.2 MVPに含めない

- Chrome拡張本体、ネイティブアプリ。
- タグ、例文、品詞、発音記号、発音再生。
- 高度な分析ダッシュボード、CSV/JSON入出力。
- `acceptable_answers` や独立した「許容回答」概念。
- `accepted` という判定種別。
- `OPEN_QUESTIONS.md` で未採用のMVP追加候補。

## 4. 機能要件

### 4.1 認証・認可

| ID | 要件 | 観測可能な条件 |
|---|---|---|
| AUTH-001 | Googleログイン | Better Auth経由でGoogle OAuth認証でき、成功後は単語一覧へ遷移する |
| AUTH-002 | ログイン必須 | 未認証時は単語・履歴・テストAPIへアクセスできず、Web画面ではログインへ誘導される |
| AUTH-003 | データ分離 | APIは本文のユーザーIDを信用せず、セッションのユーザーIDだけで読み書き対象を決める |

### 4.2 単語・意味・ヒント

| ID | 要件 | 観測可能な条件 |
|---|---|---|
| WORD-001 | 単語登録 | 英単語、1件以上の日本語の意味、任意ヒントを保存できる |
| WORD-002 | 複数意味 | 意味を追加・編集・削除でき、保存後も必ず1件以上残る |
| WORD-003 | 自分の一覧 | 単語、全意味、正解率または未回答、正解数／回答数、編集・削除を表示する |
| WORD-004 | 編集・削除 | 自分の単語だけを変更・削除できる。他ユーザーのIDは存在を推測できない応答にする |
| WORD-005 | 表示場所 | 新規登録フォームには回答回数を出さず、一覧には統計を出す |
| HINT-001 | ヒント登録 | 1単語につき0件または1件の自由記述ヒントを保存できる |
| HINT-002 | ヒント表示 | ヒントがある問題だけボタンを表示し、押すまで本文を表示しない |
| HINT-003 | 利用履歴 | 回答ごとに `hint_used` を保存し、MVPの通常正解率へ含める |

### 4.3 翻訳

| ID | 要件 | 観測可能な条件 |
|---|---|---|
| TRANS-001 | 翻訳操作 | 登録・編集画面の単語入力付近から英語→日本語の候補を要求できる |
| TRANS-002 | 登録前補助 | 候補はフォームへ反映するだけでDBへ自動保存せず、ユーザーが編集・選択できる |
| TRANS-003 | 交換可能な境界 | UIやユースケースは特定プロバイダーSDKへ直接依存せず `TranslationService` を介する |

### 4.4 テストと判定

| ID | 要件 | 観測可能な条件 |
|---|---|---|
| TEST-001 | モード選択 | 開始前に完全ランダム／苦手優先を選べる |
| TEST-002 | 完全ランダム | 認証ユーザーの登録済み単語からランダムに出題する |
| TEST-003 | 苦手優先 | 低正解率ほど選ばれやすいが、全単語に0より大きい出題可能性を残す |
| TEST-004 | 回答 | 英単語に日本語で回答し、判定後に結果と履歴を得る |
| TEST-005 | 結果表示 | 正誤、回答、登録意味、判定種別を表示し、AI判定なら明示する |
| JUDGE-001 | 判定順序 | 全登録意味に対し exact → normalized → AI の順で評価し、先に一致したら後段を呼ばない |
| JUDGE-002 | 完全一致 | 未加工文字列がいずれかの意味と一致すれば `exact` で正解にする |
| JUDGE-003 | 正規化一致 | trim、大小文字無視、全半角統一、連続空白統一後の一致を `normalized` にする |
| JUDGE-004 | AI意味判定 | 文字列一致しない場合だけ、単語・複数意味・回答を交換可能な `SemanticJudge` へ渡す |
| JUDGE-005 | 許容回答の廃止 | 正解表現は複数意味として管理し、独立した許容回答欄・テーブル・判定種別を作らない |

### 4.5 履歴・統計・可視化

| ID | 要件 | 観測可能な条件 |
|---|---|---|
| HISTORY-001 | 回答履歴 | user、word、answer、is_correct、judge_type、hint_used、answered_atを保存する |
| HISTORY-002 | 正解率 | `正解数 / 回答数` を算出し、0回答は0%ではなく未回答として返す |
| HISTORY-003 | カード色 | 未回答は白、回答済みは0%付近の赤から100%付近の黄緑へ連続的に変化させ、数値も併記する |

## 5. 画面と主要動線

| 画面 | 必須要素 |
|---|---|
| ログイン | プロダクト名、短い説明、Googleログイン |
| 単語一覧 | カード一覧、意味、統計、色、編集、削除、登録・テスト導線 |
| 単語登録／編集 | 単語、翻訳、複数意味、任意ヒント、保存、キャンセル |
| テスト設定 | 完全ランダム／苦手優先、開始 |
| テスト問題 | 英単語、回答欄、回答、条件付きヒント、二重送信防止 |
| 回答結果 | 正誤、回答、全登録意味、判定種別、次へ |

主要動線は「Googleログイン → 単語登録（必要なら翻訳）→ 一覧反映 → モード選択 → 回答（必要ならヒント）→ 履歴保存 → 統計反映」とする。

## 6. 非機能要件

### 6.1 セキュリティ

- 全ての非公開APIでセッション検証と所有者スコープを強制する。
- 更新・削除・参照は `resource_id + session.user.id` で絞り込み、本文の `user_id` は受け付けない。
- OAuth、AI、翻訳の秘密情報をブラウザー・ログ・Gitへ露出しない。
- 入力はAPI境界でスキーマ検証し、UIは未信頼文字列をHTMLとして挿入しない。
- Cookie認証の変更系リクエストはSameSite設定に加えてOriginを検証する。

### 6.2 使いやすさ・アクセシビリティ

- モバイル幅でも主要操作を完了できるレスポンシブUIを目標とする。
- 色だけに意味を持たせず、未回答／正解率／正解数／回答数を文字で示す。
- AI判定と翻訳候補は自動決定に見せず、利用箇所を明示する。
- 保存・回答の処理中は二重送信を防ぎ、失敗時は再試行可能な日本語メッセージを出す。

### 6.3 保守性・運用性

- UI、ドメインロジック、D1、AI、翻訳を境界で分離する。
- 正規化と判定順序は副作用のない関数として単体テスト可能にする。
- DBスキーマはDrizzleとマイグレーションで管理する。
- 構造化ログに `requestId`、結果、所要時間を含めるが、回答本文やトークン等の機微情報は既定で記録しない。
- バージョン、料金、モデル名、Cloudflare制限は実装開始時とデプロイ前に公式情報を再確認する。

### 6.4 性能・規模の扱い

具体的なSLO・同時接続・データ件数は未確定であり、プロダクト要件として固定しない。MVP設計では一覧のページング、履歴集計用インデックス、AIタイムアウトを用意し、実測値を記録できるようにする。想定規模を超える判断が必要な場合は `OPEN_QUESTIONS.md` を更新して承認を得る。

## 7. ユーザーストーリーと受け入れ条件

| ID | ストーリー／受け入れ条件 |
|---|---|
| AC-001 | ユーザーとしてGoogleでログインし、認証後に自分の単語一覧へ移動できる |
| AC-002 | 複数の日本語の意味と任意ヒントを持つ英単語を登録・再表示できる |
| AC-003 | 再ログイン後も自分のデータだけを参照でき、別ユーザーのデータは参照・変更できない |
| AC-004 | 翻訳候補を取得して編集でき、翻訳操作だけではDBへ単語が作成されない |
| AC-005 | 完全ランダムまたは苦手優先を選んでテストを開始できる |
| AC-006 | ヒントがある問題だけボタンが出て、押した場合だけ本文が見える |
| AC-007 | 複数意味のどれかと完全一致または必須正規化後に一致すれば、AIを呼ばず正解になる |
| AC-008 | 文字列一致しない回答だけがAI判定へ送られ、結果画面でAI利用が分かる |
| AC-009 | 正誤、判定種別、回答、ヒント利用有無、回答日時が所有ユーザーの履歴へ保存される |
| AC-010 | 一覧で単語別の正解率と正解数／回答数を確認でき、0回答は未回答と表示される |
| AC-011 | 回答済みカードは正解率に応じて赤から黄緑へ変化し、未回答は白かつ文字でも区別できる |

## 8. 前提・制約・依存

- 技術スタックの基準は TypeScript、React、TanStack Start、TanStack Router/Query、Hono、Cloudflare Workers/D1、Drizzle、Better Auth。
- Webと将来のChrome拡張は同じHono REST APIのドメイン処理を再利用する。
- AI・翻訳プロバイダーは交換可能なポート越しに利用する。
- 認証の物理スキーマは採用したBetter AuthのCLIで生成し、手作業で推測しない。
- 未確定事項は [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md) で意思決定するまで確定仕様にしない。

## 9. 最低限の検証

- ユーザー間データ分離、意味0件拒否、複数意味一致を統合テストする。
- exact／normalizedでAIが呼ばれず、不一致時だけ呼ばれることを単体・統合の両方で確認する。
- ヒントの条件表示と `hint_used`、未回答と0%の区別、翻訳だけで未保存を確認する。
- 主要動線 AC-001〜AC-011 をテストケースへ追跡可能にする。
